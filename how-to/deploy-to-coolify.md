# Deploy to Coolify

How to deploy or update Catena on a Coolify-managed host. Local/self-hosted mode still deploys the full Supabase stack. Cloud mode deploys only the dashboard in Coolify and uses Supabase Cloud for DB/Auth/Storage; see [ADR-040](https://github.com/gidorah/catena/blob/dev/decisions/040-supabase-cloud-bridge.md) and [ADR-043](https://github.com/gidorah/catena/blob/dev/decisions/043-cloud-mode-compose-artifact.md).

This is a **how-to**, not a tutorial:

- It does not teach Coolify or Docker Compose.
- It does not cover SSL/TLS or domain setup — Coolify handles that via its UI on top of Traefik.
- It does not cover how to provision the Coolify host itself.

## What gets deployed

Catena has two deploy artifacts:

1. **Self-hosted mode:** `docker-compose.yml` deploys the full Supabase stack plus the dashboard. Local dev layers `docker-compose.local.yml` on top via `npm run docker:up`.
2. **Cloud mode:** `docker-compose.cloud.yml` deploys only the dashboard service. Supabase Cloud hosts Postgres, Auth, Storage, and PostgREST. This artifact has no fixed top-level Compose name and no fixed `container_name`, so staging and production resources can coexist on one host.

Self-hosted mode has two pieces, both defined in the canonical `docker-compose.yml`:

1. **The full Supabase stack** — Postgres, Kong, GoTrue (auth), PostgREST, Realtime, Storage, ImgProxy, Edge Functions, Logflare/Vector, Supavisor pooler, Studio, plus the one-shot `migrator`. 14 containers (counting `meta`, `vector`, and `migrator`) wired on a single Docker network (`catena-network`), no host port bindings — Coolify/Traefik fronts the public surface.
2. **The Next.js dashboard** in standalone mode — built from `Dockerfile.self-hosted` (multi-stage: `deps` → `builder` → `runner`). The runner image runs `node apps/dashboard/server.js`; that `server.js` is **generated by `next build`**, not present in source. The runner exposes port 3000.

Total: 15 services (14 Supabase/support services + 1 dashboard). The `migrator` is expected to exit successfully after applying or skipping migrations. The Compose migrator ([ADR-039](https://github.com/gidorah/catena/blob/dev/decisions/039-compose-migrator-service.md), [ADR-042](https://github.com/gidorah/catena/blob/dev/decisions/042-storage-bootstrap-before-app-migrator.md)) applies only to local/self-hosted mode; Cloud staging and production use `.github/workflows/cloud-migrations.yml` with Supabase CLI remote history instead of `public.schema_migrations`.

Cloud mode has one service: the Next.js dashboard built from the same `Dockerfile.self-hosted`. It excludes `db`, `kong`, `auth`, `rest`, `storage`, Studio, Logflare/Vector, Supavisor, and the Compose `migrator`.

## Prerequisites

- A Coolify host with Docker, with enough RAM for the Supabase stack plus the dashboard build (see "Operational gotchas" below for the swap requirement).
- A new Coolify Project pointing at the deploy branch. Use `docker-compose.yml` for self-hosted mode. For Cloud mode, use `docker-compose.cloud.yml`, keep raw Git-push auto-deploy disabled, and let `.github/workflows/cloud-migrations.yml` trigger deployments through the Coolify API. Production Cloud resources must not track `dev`; they are deployed automatically by the workflow after `v*` tag pushes trigger the release pipeline. Pre-existing self-hosted apps that still point at `docker-compose.self-hosted.yml` need a one-time UI reconfiguration; see [ADR-038](https://github.com/gidorah/catena/blob/dev/decisions/038-single-canonical-compose-with-local-overlay.md).
- The relevant env vars from `.env.example` and `apps/dashboard/.env.example` populated in the Coolify project's **Environment Variables** tab — see "Environment variables" below.
- A domain (or subdomain) routed at the Coolify host so Traefik can issue TLS certs.

## Build and deploy

### Self-hosted mode

1. Push to the deploy branch.
2. Before the first deploy that enables the Compose migrator on an existing database, run the production migration-history preflight below. Skip this only for a brand-new empty database.
3. In Coolify → the project → **Deploy**. Coolify clones the repo, builds the `dashboard` service from `Dockerfile.self-hosted`, builds the `db` service from `docker/volumes/db/Dockerfile`, builds the `migrator` service from `docker/migrations/Dockerfile`, pulls the upstream Supabase images, and brings everything up via `docker compose`.
4. The `migrator` service runs `supabase/migrations/*.sql` after Supabase Storage has bootstrapped its own schema. Migration files and the runner script are baked into the migrator image; they are not runtime bind mounts.
5. Watch Coolify → **Logs** for `migrator`. A successful deploy shows the migrator applying or skipping each migration, notifying PostgREST to reload its schema cache, then exiting 0. Public entrypoints (`kong` and `dashboard`) wait for `migrator: condition: service_completed_successfully`.
6. If the migrator exits non-zero, treat the deploy as failed. Inspect the migrator logs first; failed migrations are not recorded in `public.schema_migrations`, and public entrypoints should not start against the stale schema.
7. Hit the public URL. You should land on the login page; sign-up should write to `auth.users`.

The `migrations.yml` GitHub Action in `.github/workflows/` validates migration PRs against a disposable local Supabase CLI database and pgTAP. It does **not** apply migrations to a Coolify-self-hosted database; Coolify deploys still use the Compose `migrator` service described above.

### Cloud mode

Cloud mode uses `docker-compose.cloud.yml` and must be deployed through `.github/workflows/cloud-migrations.yml`, not raw Git push auto-deploy. Job order, identity chain, and staging vs production behavior are documented in [`../explanation/ci-cd-pipeline.md`](https://github.com/gidorah/catena/blob/dev/explanation/ci-cd-pipeline.md). Day-to-day release steps: [`work-with-prs-staging-and-releases.md`](/how-to/work-with-prs-staging-and-releases).

Coolify-specific requirements:

- Disable raw Git-push auto-deploy on Cloud staging and production resources so migrations always precede deploy and SHA pinning is enforced.
- Provide build/runtime env vars listed under "Environment variables" below, including `CATENA_DEPLOY_SHA` pinned by the workflow before each deploy.
- Staging applies on every push to `dev`; production applies on SemVer `v*` tag pushes after `main` is fast-forwarded from a staging-validated SHA.

### Cloud production bootstrap

One-time empty production Supabase projects cannot use the normal tag path until remote migration history exists. Run **workflow_dispatch** on `cloud-migrations.yml` with these inputs (names must match the workflow form):

| Input | Value |
| ----- | ----- |
| `environment` | `production` |
| `target_sha` | 40-character commit SHA for the bootstrap release |
| `production_release_tag` | Protected tag whose commit equals `target_sha` and `origin/main` |
| `apply_migrations` | `true` |
| `trigger_deploy` | `true` |
| `allow_include_all` | `true` |
| `confirm_empty_production_bootstrap` | `EMPTY-PRODUCTION-CLOUD-BOOTSTRAP` |
| `confirm_production_apply` | Same value as `target_sha` |

After bootstrap, normal releases use SemVer tags only; do not use `--include-all` on recurring production applies. Phase 0 `prod-YYYYMMDD-<sha>` tags remain accepted for manual dispatch during transition.

Release checklist and pipeline architecture: [`work-with-prs-staging-and-releases.md`](/how-to/work-with-prs-staging-and-releases), [`../explanation/ci-cd-pipeline.md`](https://github.com/gidorah/catena/blob/dev/explanation/ci-cd-pipeline.md).

When rendering `docker-compose.cloud.yml` outside Coolify, set `COMPOSE_PROJECT_NAME` or pass `docker compose -p` with an environment-specific name such as `catena-cloud-staging` or `catena-cloud-production`. The committed Cloud compose file intentionally has no top-level `name:` and no fixed `container_name`; Docker Compose may still derive a local project name from the checkout directory when no project name is supplied.

### Cloud dashboard URLs

Catena's Cloud staging and production dashboard hosts (also baked into `cloud-migrations.yml`, `next.config.mjs`, and Cloud smoke guards):

| Environment | Dashboard URL |
| ----------- | ------------- |
| Staging | `https://dashboard.staging.catena.onur.sh` |
| Production | `https://dashboard.prod.catena.onur.sh` |

These are the values to use for manual `/api/health/version` checks and for `BASE_URL` when reproducing Cloud smoke locally. Changing hosts requires updating the workflow YAML and the dashboard config allowlists — Coolify env vars alone are not sufficient.

### Supabase Cloud auth checklist

Configure **each** Supabase Cloud project (staging and production) separately in the dashboard under **Authentication → URL Configuration**. New projects ship with Site URL `http://localhost:3000/`; leaving that default breaks sign-up confirmation emails even when Coolify env vars are correct.

| Check | Staging | Production |
| ----- | ------- | ---------- |
| **Site URL** | `https://dashboard.staging.catena.onur.sh` | `https://dashboard.prod.catena.onur.sh` |
| **Redirect URLs** | `https://dashboard.staging.catena.onur.sh/auth/confirm`<br>`https://dashboard.staging.catena.onur.sh/auth/callback` | `https://dashboard.prod.catena.onur.sh/auth/confirm`<br>`https://dashboard.prod.catena.onur.sh/auth/callback` |

Add the exact paths above. Redirect requests include query strings (`?next=…`, Supabase `token_hash`, `code`, etc.). If Supabase rejects a redirect as disallowed, add wildcard suffixes per [Supabase redirect URL docs](https://supabase.com/docs/guides/auth/redirect-urls) (for example `https://dashboard.staging.catena.onur.sh/auth/confirm**`).

Coolify: set `NEXT_PUBLIC_SITE_URL` at **build and runtime**; set `SITE_URL` at **runtime only** (same HTTPS origin as the Supabase Site URL). The dashboard passes `emailRedirectTo` / `redirectTo` from `NEXT_PUBLIC_SITE_URL` in `signUpAction` and `requestPasswordResetAction`; `/auth/confirm` and `/auth/callback` also fall back to `SITE_URL` when resolving redirect origins. Supabase still requires matching entries in the redirect allowlist.

Also configure **SMTP** (or verify built-in mail works) and ensure **email confirmation** is enabled — without mail delivery or confirmation, register/login flows fail regardless of redirect URLs. If Google sign-in is enabled, configure the Google provider in Supabase and set the Google Cloud authorized redirect URI to `https://<dashboard-host>/auth/callback` for that environment.

After any auth URL change, verify end-to-end on that environment:

1. Register a new account — confirmation email link must point at `https://dashboard.staging.catena.onur.sh/auth/confirm` (or the production host), not localhost.
2. Click the link — user lands on `/[locale]/dashboard/default` with a session.
3. Request password reset — link must use `/auth/callback?next=…/v1/update-password`.

Old confirmation emails keep their original redirect; re-register or resend after fixing config.

## Environment variables

`.env.example` (root) and `apps/dashboard/.env.example` together form the canonical reference. Read them directly — this doc deliberately does not duplicate the full variable list.

Self-hosted mode variables:

- **Set every secret marked `CHANGE_ME_IN_PRODUCTION`** (`POSTGRES_PASSWORD`, `JWT_SECRET`, `SECRET_KEY_BASE`, `VAULT_ENC_KEY`, `PG_META_CRYPTO_KEY`, `LOGFLARE_*_ACCESS_TOKEN`). The `JWT_SECRET` must be ≥ 32 characters; the JWT-based `ANON_KEY` and `SERVICE_ROLE_KEY` must be re-issued to match it.
- **Also change `DASHBOARD_USERNAME` and `DASHBOARD_PASSWORD`** even though they are not tagged `CHANGE_ME_IN_PRODUCTION`. They default to `supabase`/`supabase` in `.env.example` and gate Studio's basic-auth via Kong.
- **`SITE_URL` and `SUPABASE_PUBLIC_URL` must be the public HTTPS URLs**, not `localhost`. GoTrue uses `SITE_URL` to build redirect URLs in confirmation emails.
- The dashboard reads **`SUPABASE_URL`** server-side and **`NEXT_PUBLIC_SUPABASE_URL`** in the browser. In `docker-compose.yml` the dashboard service hard-codes `SUPABASE_URL=http://kong:8000` while `NEXT_PUBLIC_SUPABASE_URL` is set from `SUPABASE_PUBLIC_URL`. Don't collapse them.
- `ANTHROPIC_API_KEY` is read from the Coolify env and passed into the dashboard container; required only for the AI category-suggestion path.

For both modes, `NEXT_PUBLIC_*` vars must also be present at **build time** because Next.js inlines them into client bundles. Set these in Coolify's **Build Variables** pane, not just Environment Variables. Runtime-only public values produce a server that boots fine but ships broken client bundles, with no obvious error.

Cloud mode build variables:

- `CATENA_SUPABASE_MODE=cloud`

- `CATENA_EXPECTED_SUPABASE_PROJECT_REF`
- `NEXT_PUBLIC_SUPABASE_URL`
- `NEXT_PUBLIC_SUPABASE_ANON_KEY`
- `NEXT_PUBLIC_SITE_URL`
- `CATENA_DEPLOY_SHA`

- `SENTRY_PROJECT` (defaults to `dashboard` when omitted)
- `SENTRY_AUTH_TOKEN` (secret; required for source-map upload during Coolify builds)

Cloud mode runtime variables:

- `NODE_ENV=production` (**runtime only** in Coolify — do not enable "Available at Buildtime". Coolify injects build-time `NODE_ENV=production` into Docker builds and can break `pnpm install` / `next build`; the runner image and `docker-compose.cloud.yml` still set production at runtime.)
- `CATENA_SUPABASE_MODE=cloud`
- `CATENA_DEPLOY_ENV=staging` or `production`
- `CATENA_EXPECTED_SUPABASE_PROJECT_REF`
- `CATENA_DEPLOY_SHA`
- `NEXT_PUBLIC_SUPABASE_URL`

- `NEXT_PUBLIC_SENTRY_DSN`

Set Sentry build variables on **both** Cloud Coolify resources (staging and production). Use the same Sentry project DSN on both; the dashboard tags events with `environment=staging` or `environment=production` from `CATENA_DEPLOY_ENV`, and `release` from `CATENA_DEPLOY_SHA` / `CATENA_BUILD_SHA` (matching `/api/health/version`). Store `SENTRY_AUTH_TOKEN` only in Coolify **Build Variables**, never in runtime env or GitHub Actions unless you later want CI source-map uploads. Create the token in Sentry under **Settings → Auth Tokens** with `project:releases` and `org:read` scopes. See [ADR-044](https://github.com/gidorah/catena/blob/dev/decisions/044-sentry-error-monitoring.md).

Self-hosted Coolify deployments are out of scope for Sentry in MVP; only Cloud staging/production resources should set these vars.

Cloud GitHub Environment values:

Configure secrets and variables on two GitHub Environments: **`supabase-staging`** (staging migration/deploy/smoke jobs) and **`supabase-production`** (production dry-run and apply jobs).

- `SUPABASE_ACCESS_TOKEN`, `SUPABASE_PROJECT_REF`, `SUPABASE_DB_PASSWORD`, and `NEXT_PUBLIC_SUPABASE_ANON_KEY` for each environment.
- `CATENA_STAGING_SUPABASE_PROJECT_REF` as a non-secret staging environment variable. It must equal the staging `SUPABASE_PROJECT_REF`; the migration and smoke jobs use it as an independent allowlist.
- `PRODUCTION_CATENA_EXPECTED_SUPABASE_PROJECT_REF` as a non-secret production environment variable. It must equal the production `SUPABASE_PROJECT_REF`; production dry-run/apply jobs use it as an independent allowlist.
- `COOLIFY_API_BASE_URL`, `COOLIFY_API_TOKEN`, `COOLIFY_STAGING_RESOURCE_ID` for staging deploys, and `COOLIFY_PRODUCTION_RESOURCE_ID` for production deploys.
- `CATENA_E2E_USER_EMAIL`, `CATENA_E2E_USER_PASSWORD`, `CATENA_E2E_SECOND_USER_EMAIL`, and `CATENA_E2E_SECOND_USER_PASSWORD` for staging smoke login checks.
- `CATENA_E2E_SERVICE_ROLE_KEY` for staging smoke setup and cleanup only.

Do not pass `SUPABASE_SERVICE_ROLE_KEY` into the Cloud dashboard runtime or guarded Playwright runners. The staging Cloud smoke suite may use `CATENA_E2E_SERVICE_ROLE_KEY` only inside the GitHub Actions runner for setup and cleanup.

Protect the `supabase-production` GitHub Environment with required reviewers when the repository plan supports them. The production pipeline targets this environment in both the dry-run and apply jobs, so paid plans with required reviewers enabled will prompt twice per release. Private GitHub Free repositories cannot use environment required reviewers, so the production tag push is the release trigger and there is no approval pause on that plan.

### GitHub repository protection (Cloud production)

Configure these once in the GitHub repository UI before relying on tag-driven production releases:

1. **Tag protection (`v*`).** Settings → Tags → Add tag protection rule. Set the pattern to `v*`. Restrict tag creation and push to repository administrators (or the release operator account). This blocks accidental or unauthorized release tags and prevents tag force-push or deletion.
2. **`supabase-production` environment gate.** Settings → Environments → `supabase-production` → enable **Required reviewers** and add the release operator account.
3. **Double-approval expectation.** Both **Production Cloud Dry Run** and **Production Cloud Apply** target `supabase-production` to read database credentials, so GitHub prompts for approval twice per release when required reviewers are enabled: once before the dry-run, and again before the final apply and deploy. This is expected.

Protect `main` and the production tag pattern when repository rulesets are available. Production tags must not be moved or reused after creation. The workflow compares the peeled tag commit (`tag^{commit}`) to `origin/main` and `target_sha`, so annotated tags are safe as long as the tag points at the release commit.

## Operational gotchas

These have all bitten the project at least once. Don't rediscover them.

- **Keep `console.error` / `console.warn` in production builds.** Container logs are the primary incident-response surface; stripping them blinds Coolify's log view.
- **Enable swap on the Coolify host before overlapping dashboard builds.** `next build` spikes memory hard, and an OOM during a build leaves the previous container running but shows a confusing red state in Coolify.
- **Keep `NODE_ENV` runtime-only in Coolify Cloud resources.** Uncheck "Available at Buildtime" for `NODE_ENV` on staging and production dashboard apps. Production console stripping during `next build` uses `CATENA_DEPLOY_ENV` in `next.config.mjs` when `NODE_ENV` is unset in the builder stage.
- **Multipart uploads need the proxy matcher _and_ bounded parsing.** `apps/dashboard/src/proxy.ts` excludes `/api/*`, `/auth/*`, and `/monitoring` from `config.matcher` so route handlers and the Sentry tunnel receive unconsumed request bodies. Do not remove that exclusion when adding routes — `proxy.test.ts` guards segment boundaries. The project document route then reads `request.arrayBuffer()` and uses the bounded parser in `apps/dashboard/src/lib/multipart-upload.ts` to extract only the expected `file` part. Calling `request.formData()` directly, or reconstructing a `Request` and calling `.formData()`, has failed on this path for deployed browser uploads. Reuse both patterns in any new deployed file-upload route.
- **Stop after the first failed staging Cloud workflow.** The staging workflow mutates the Cloud database and triggers a live Coolify deploy after migration verification. If any staging run fails, pause and inspect the failed step before merging another fix to `dev`; do not create a merge-fix-merge loop.
- **Production and staging deploys are SHA-pinned and post-verified.** Raw Git push auto-deploy on Cloud Coolify resources must stay disabled. The workflow writes `CATENA_DEPLOY_SHA` to the Coolify resource environment, triggers deploy through the Coolify API, then verifies Coolify's reported commit and `/api/health/version`. A mismatch after migrations have been applied is caught before the workflow exits and is surfaced as a workflow failure. Ensure the Coolify resource is configured to rebuild on deploy so the pinned build arg is picked up.
- **Production Cloud bootstrap is one-time and explicit.** Empty production projects may use `supabase db push --include-all` only through manual `workflow_dispatch` with `confirm_production_apply` matching the target SHA, `confirm_empty_production_bootstrap=EMPTY-PRODUCTION-CLOUD-BOOTSTRAP`, and an empty-project preflight. Normal recurring production applies must not use `--include-all`.
- **`kex_exchange_identification` errors during deploy** are SSH connection-limit failures on the host, not an app problem. Raise `MaxStartups` and `MaxSessions` in the host's `sshd_config` and reload sshd; do not attempt to fix this in app code.
- **Don't bind-mount repo files into runtime containers.** Coolify writes the rendered compose to `/data/coolify/applications/<uuid>/` but does **not** sync `docker/volumes/` (or any other repo subtree) to the host. A bind mount whose source path is missing is silently auto-created as an empty _directory_ by the Docker daemon, which then breaks `entrypoint:` / `command:` resolution and persists across redeploys. Repo files needed at runtime (entrypoint scripts, declarative configs) must be baked into the image via `build:` + `COPY` — see [ADR-038](https://github.com/gidorah/catena/blob/dev/decisions/038-single-canonical-compose-with-local-overlay.md) "Bind-mount-source delivery regression" for the kong precedent. Bind mounts remain appropriate for host-managed paths (sockets, Coolify-owned volume dirs) and files set up via Coolify's File Mount UI.
- **Postgres major-version changes require a volume migration plan.** The current self-hosted image is Postgres 17. Existing Postgres 15 volumes cannot be started by the Postgres 17 image in place. For disposable local/dev stacks, run `npm run docker:clean`. For any non-disposable Coolify stack, take a dump and restore into a fresh Postgres 17 volume or run a reviewed `pg_upgrade` plan before deploying the image change.
- **The migrator's exited state is expected.** The canonical Compose file intentionally does not include Coolify's non-standard `exclude_from_hc` key because local Docker Compose rejects it during config parsing. A failed migrator blocks `rest` and `dashboard`; a successful exited migrator is normal. If Coolify marks the exited migrator as unhealthy, handle that in Coolify after validating the deployed version's behavior rather than breaking local Compose validation.
- **Never apply `,z` / `,Z` to socket bind mounts.** SELinux relabeling a Unix domain socket can change its context in ways that break the docker daemon's own use of it, surfacing as silent socket-access failures inside the container (e.g. vector failing its `:9001/health` probe). Regular files and directories are fine; sockets are not. See [ADR-038](https://github.com/gidorah/catena/blob/dev/decisions/038-single-canonical-compose-with-local-overlay.md) "Bind-mount regression caught at first Coolify deploy".

## Self-hosted migrator rollout preflight

Before enabling the Compose migrator on an existing production database, compare the rows in `public.schema_migrations` with the stems of `supabase/migrations/*.sql` from the exact commit being deployed. Stop the rollout if any version is missing, extra, malformed, duplicated, or if `public.schema_migrations.version` is not unique.

Run database commands through the Compose service name, not fixed container names. On the Coolify host, use the rendered application directory for the existing deployment:

```bash
docker compose exec -T db psql -U supabase_admin -d postgres \
  -c "select version from public.schema_migrations order by version;"
```

For a machine-readable check, write the DB output and repo filenames to two sorted files and compare them:

```bash
docker compose exec -T db psql -U supabase_admin -d postgres -At \
  -c "select version from public.schema_migrations order by version;" > /tmp/db-migrations.txt
ls supabase/migrations/*.sql | xargs -n1 basename | sed 's/\.sql$//' | sort > /tmp/repo-migrations.txt
diff -u /tmp/db-migrations.txt /tmp/repo-migrations.txt
```

## Self-hosted rollback

Coolify retains previous images. To roll back:

1. **Take a Postgres dump first** — there is no automated DB rollback, and step 2 may need it:
   ```bash
   # SSH to the Coolify host, then:
    docker compose exec -T db pg_dump -U supabase_admin -d postgres > rollback-pre-$(date +%Y%m%d-%H%M%S).sql
   ```
2. Coolify → project → **Deployments** → pick the last-known-good deployment → **Redeploy**.
3. If the rollback target predates a database migration that has already been applied, the older app version may not start cleanly against the newer schema. Most migrations in `supabase/migrations/` have **no reverse script** — drops, type narrowings, and constraint additions are one-way. You either roll forward (deploy a fix-up migration) or restore from the dump in step 1. Improvising a manual revert in Studio's SQL editor is a data-loss path; do not.
4. Verify by hitting the public URL and walking through login + project creation.

## Cloud production rollback

Cloud production has no automated schema rollback. Use these paths depending on what failed:

1. **App-only rollback (schema unchanged).** Coolify → production Cloud resource → **Deployments** → redeploy the last-known-good deployment. Verify `/api/health/version` reports the expected commit. Only safe when the current release's migrations already match what the older app expects.
2. **Migrations applied, deploy failed.** Do not create a new tag. Fix Coolify config or credentials, then use emergency manual `workflow_dispatch` on `cloud-migrations.yml` with the same `target_sha` and `production_release_tag` — see [`work-with-prs-staging-and-releases.md`](/how-to/work-with-prs-staging-and-releases).
3. **Bad schema migration shipped.** There are no down migrations — roll **forward** with a fix migration on `dev`, re-validate staging, and cut a new release tag.
4. **Database restore.** Use Supabase Cloud backup/PITR for the production project. Never run `supabase db reset`, seed scripts, or destructive pgTAP against Cloud staging or production.

For self-hosted full-stack rollback (Compose migrator path), see [Self-hosted rollback](#self-hosted-rollback) above.

## Historical ADR-034 Context

The pre-MVP topology used Vercel for the dashboard and per-PR Supabase Cloud preview branches. Combined cost exceeded the MVP budget, so the Vercel-related GitHub Actions workflows were deleted in Phase A of the docs reconstruction. ADR-034 remains the historical reason the project standardized on Coolify for application hosting, but ADR-040 supersedes it for the backend target: Cloud mode uses Coolify for the dashboard and Supabase Cloud for database, Auth, Storage, and migration history.
